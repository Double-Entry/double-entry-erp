# Development

> **TL;DR:** `bench start` boots every process listed in `frappe-bench/Procfile` under a single `honcho`-style supervisor — Redis (three instances), SocketIO, the file watcher, the scheduler, the web server, and a worker. The web server answers on `:8000`. Migrations live in `erpnext/patches/` and run via `bench --site <site> migrate`.

## `bench start` and the Procfile

`bench init` writes a `Procfile` into the bench root. Each line is `<name>: <command>`. `bench start` runs them all concurrently, multiplexing stdout into a single stream.

Based on the sed commands the CI installer applies to neutralise lines — [.github/helper/install.sh:64](../../.github/helper/install.sh:64):

```bash
sed -i 's/watch:/# watch:/g'           Procfile
sed -i 's/schedule:/# schedule:/g'     Procfile
sed -i 's/socketio:/# socketio:/g'     Procfile
sed -i 's/redis_socketio:/# redis_socketio:/g' Procfile
```

— these are the four processes CI disables. That implies the full local `Procfile` contains at least the following named processes:

| Process | Role |
|---|---|
| `redis_cache` | Redis instance for `frappe.cache()` (LRU app cache). |
| `redis_queue` | Redis instance for RQ job queue. |
| `redis_socketio` | Redis instance used as Socket.IO pub/sub. Commented out in CI. |
| `socketio` | Node SocketIO server for real-time updates (form reloads, notifications). Commented out in CI. |
| `watch` | Frontend asset watcher (esbuild / rollup). Commented out in CI. |
| `schedule` | Scheduler process that dispatches `scheduler_events` from hooks. Commented out in CI. |
| `web` | Gunicorn/werkzeug HTTP server on `:8000`. |
| `worker` | RQ worker consuming `redis_queue`. |

### Typical local boot

```bash
cd ~/frappe-bench
bench start
```

Logs stream to the terminal. For a backgrounded bench (CI style), redirect:

```bash
bench start &>> ~/frappe-bench/bench_start.log &
```

See [install.sh:76](../../.github/helper/install.sh:76). Retrieve logs later with `tail -f ~/frappe-bench/bench_start.log`.

### Why three Redis instances

Frappe splits caching, queuing, and pub/sub across three Redis instances to isolate eviction policy and memory pressure. Killing `redis_cache` does not lose queued background jobs; killing `redis_queue` does not kill live SocketIO sessions.

## Hot reload

The `watch` Procfile process runs the asset bundler in watch mode. JS/CSS/SCSS edits rebuild automatically; reload the browser manually. Python edits require a restart of the `web` / `worker` processes — the framework does **not** auto-reload Python (Frappe's app caching is too aggressive for safe autoreload).

```bash
bench restart                 # restarts gunicorn + workers in-place
bench restart --web           # web only
bench restart --supervisor    # production (systemd/supervisor-based)
```

## Accessing the database

Use the `bench mariadb` / `bench postgres` shortcuts — they read `site_config.json` and pass the right credentials:

```bash
bench --site mysite.localhost mariadb     # interactive MariaDB shell for the site
bench --site mysite.localhost postgres    # interactive psql for the site
```

No site flag → uses the bench's `common_site_config.json` creds for DB-admin work.

Every DocType has a MariaDB table named `tab<DocType Name>` — e.g. `tabSales Invoice`, `tabGL Entry`, `tabStock Ledger Entry`. Column names mirror DocType field names 1:1.

## Python REPL

```bash
bench --site mysite.localhost console
```

Drops you into a Python shell with `frappe` already imported and a live DB connection to the site. Useful for:

- Inspecting docs: `frappe.get_doc("Sales Invoice", "SI-00001")`.
- Running a controller method by hand.
- Reproducing a production bug against staging data.

All mutations auto-commit at exit unless you `frappe.db.rollback()` explicitly.

## Migrations and patches

`bench migrate` walks the registered patches plus schema sync:

```bash
bench --site mysite.localhost migrate
```

Steps executed:

1. Run every patch in `erpnext/patches/pre_model_sync` block of [erpnext/patches.txt](../../erpnext/patches.txt:1).
2. Sync every DocType JSON into DB (create/alter tables).
3. Run every patch in the `post_model_sync` block.
4. Re-run fixtures (roles, workflows, custom fields declared via hooks).

Full semantics are documented in [patterns/patches.md](../patterns/patches.md) — including how to add a new patch and when to use pre vs post.

`bench migrate` is **idempotent**: re-running it after success is a no-op. Already-executed patches are recorded in the `tabPatch Log` table.

## Editing DocTypes

Via the UI — Menu → Customise → `DocType`. The changes write back to the `.json` file on disk **only** when the site is in "Developer Mode" (`developer_mode = 1` in `site_config.json`). Without dev mode, DocType edits in the UI are stored as `Custom Field` / `Property Setter` overlays and **not** reflected in the repo.

```bash
bench --site mysite.localhost set-config developer_mode 1
```

## Clearing caches

Frappe caches aggressively — meta, permissions, translations, boot session. After low-level changes:

```bash
bench --site mysite.localhost clear-cache        # per-site
bench --site mysite.localhost clear-website-cache # portal/website only
```

Full restart equivalent:

```bash
bench restart && bench --site mysite.localhost clear-cache
```

## Building assets

During development `bench start` keeps assets fresh via `watch`. Production and any manual rebuild go through:

```bash
bench build              # all apps
bench build --app erpnext
```

The result lands in `sites/assets/erpnext/dist/`.

## Debug tips

- **Set breakpoints:** add `breakpoint()` in any controller and hit the route. Execution pauses in the `web` process's console (check the terminal running `bench start`).
- **Server logs:** `bench --site mysite.localhost browse` hints at routes; real logs are in `logs/web.log`, `logs/worker.log`, `logs/scheduler.log` inside the bench directory.
- **Error Log DocType:** every unhandled exception lands in `Error Log` — navigate in the UI or `frappe.get_all("Error Log", order_by="creation desc", limit=10)` in `bench console`.
