1. Выбери форму развёртывания (см. «File layout» ниже):
   • Авто-регистрируемый скилл  → `.claude/skills/<skill-name>/SKILL.md`
   • Reference-only скилл       → `.claude/skills/<topic>/skill-<name>.md` (любое имя)
2. Скопируй файл по выбранному пути.
3. Обнови frontmatter: `name`, `description` (TRIGGER + SKIP).
4. Заполни 12 каноничных разделов domain-specific деталями.
5. Держи скилл **самодостаточным** — читатель должен уметь оперировать в твоём

6. Удали все `<!-- -->` комментарии-подсказки перед релизом.
7. Английская версия — `.claude/skills/example/skill-template.md`.

 ЧТО ТАКОЕ СКИЛЛ (И ЧЕМ ОН НЕ ЯВЛЯЕТСЯ)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Скилл — **самодостаточная база знаний** в markdown-форме. Он:
  • Захватывает экспертное знание домена, на которое модель может опереться в задаче.
  • Живёт в `.claude/skills/`, так что Claude Code (и твои агенты) могут его найти.
  • Либо *авто-регистрируем* (строгое имя файла), либо *reference-only* (кастомное).

Скилл НЕ:
  • Агент. Скиллы ПАССИВНЫЕ ссылки; агенты АКТИВНЫЕ исполнители.
  • Команда. Команды — тонкие обёртки делегирования.
  • Одноразовая инструкция. Скиллы должны быть переиспользуемы между сессиями.
  • Мнение. Скиллы кодифицируют факты, каноничные источники, фреймворки.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 РАЗМЕЩЕНИЕ ФАЙЛА — ДВЕ ФОРМЫ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ФОРМА A — АВТО-РЕГИСТРИРУЕМАЯ (конвенция Claude Code)
  Путь:     .claude/skills/<skill-name>/SKILL.md
  Имя:      строго "SKILL.md" (заглавные).
  Эффект:   Харнес сканирует и регистрирует как скилл `<skill-name>`; авто-матчит
            по description в релевантных сессиях; вызывается через Skill tool.

ФОРМА B — REFERENCE-ONLY (плоская или иерархическая с кастомными именами)
  Путь:     .claude/skills/<anything>/skill-<name>.md (любое имя)
  Эффект:   НЕ авто-регистрируется харнесом. Работает только когда агент
            Read'ит его по явному пути (Правило: «Читай
            .claude/skills/legal/skill-legal-ru.md перед написанием RU-секции»).
  Плюсы:    Кастомные иерархии возможны; человеко-читаемые имена; нет случайного
            авто-матчинга на несвязанных задачах.
  Минусы:   Нет харнес-авто-триггера; нет вызова через Skill tool; нет discovery
            по description-matching в свежих сессиях.

ЧТО ВЫБРАТЬ
  • Авто-регистрация (Форма A) когда: скилл широко применим и пользователь выигрывает
    от того, что он всплывает в релевантных сессиях сам.
  • Reference-only (Форма B) когда: скилл нагружен для конкретного агента, правила
    агента предписывают явные чтения по пути, и ты хочешь избежать срабатывания
    скилла на несвязанных сессиях.

 BEST PRACTICES СКИЛЛОВ CLAUDE CODE — КРАТКИЙ СПРАВОЧНИК

FRONTMATTER
  • `name`        — kebab-case; совпадает с директорией (Форма A) или выбранным
                   идентификатором (Форма B).
  • `description` — 1 абзац, плотный ключевыми словами; начинается с TRIGGER-условий
                   и заканчивается SKIP-условиями. Определяет авто-матчинг в Форме A.
  • Кастомные поля (опционально): `version`, `updated`, `authoritative-sources`.

КАНОНИЧНАЯ 12-РАЗДЕЛЬНАЯ СТРУКТУРА
  1. Статус юрисдикции/домена и правовая/концептуальная традиция.
  2. Основные статуты / стандарты / спеки — с operational-значением по каждому.
  3. Framework контрактов / взаимодействия / формирования (если применимо).
  4. Связанные / смежные регуляции или стандарты.
  5. Международные / кросс-доменные обязательства.
  6. Case law / прецеденты / референсные реализации + иерархия судов/органов.
  7. Авторитетные органы — кто публикует, кто интерпретирует.
  8. Каноничные источники (для WebFetch-верификации).
  9. Применение скилла к стандартной output-структуре (секция «как делать»).
 10. Типичные ошибки — явный список того, чего избегать.
 11. Output-ограничения — стиль цитирования, форматы идентификаторов.
 12. Последствия для {{основного контекста проекта}} — что скилл конкретно значит
     для проекта, в котором он размещён.

Не каждому скиллу нужны все 12 — обрезай до минимально полезного набора для домена.
Юридические скиллы обычно используют все 12. Технические могут 7-8. Reference-ADR
скиллы могут 4-5.

ПРАВИЛО САМОДОСТАТОЧНОСТИ
  Файл скилла должен быть читабелен и operable БЕЗ внешнего контекста. Читатель
  открывает, понимает что покрыто, знает как применить. Внешние ссылки должны быть
  явно помечены — "(canonical source: URL)" или "см. также
  .claude/skills/<other-skill>/SKILL.md".

ИСПОЛЬЗОВАНИЕ ТАБЛИЦ
  Используй markdown-таблицы активно для:
    • Статей статута/стандарта с однострочными operational-значениями.
    • Цитат дел со сводкой holding.
    • Матриц сравнения (совместимость, юрисдикции).
    • URL каноничных источников.

ДИСКЛЕЙМЕР
  Если скилл совещательный (legal / medical / safety), открывай секцию 1
  blockquote-дисклеймером:
    > **Дисклеймер.** Этот скилл предоставляет информационный справочный материал...

СТИЛЬ ЦИТИРОВАНИЯ
  • Каноничный идентификатор сначала, человеко-описание потом.
    Хорошо: «§ 106(3) US Copyright Act — право распространения».
    Плохо:  «право распространения (§ 106(3))».
  • Сохраняй оригинальные скрипты и каноничные формы (кириллица статутов,
    курсив имён дел, SPDX ID).
  • Помечай неопределённость `TODO(verify)` с конкретным открытым вопросом.
