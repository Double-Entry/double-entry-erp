## Что такое хуки (и чем они не являются)

**Хук** — shell-команда, которую харнес Claude Code выполняет в ответ на lifecycle-событие. Хуки — механизм **детерминированного автоматического поведения** — того, что модель сама надёжно обеспечить не может, потому что это должно происходить стабильно и вне контроля модели:

- Pre-проверка `Bash`-команды до её запуска моделью.
- Авто-форматирование файла после того, как модель его написала.
- Добавление в audit-лог каждый раз, когда пользователь отправляет промпт.
- Показ кастомного summary, когда модель заканчивает turn.
- Блокировка permission-sensitive операций.

Хуки НЕ:
- Место для логики рассуждений модели — если решение «делать ли X», решает модель, не хук.
- Замена правилам агента — хуки это тупые pre/post фильтры, не структурированные рассуждения.
- Часть разговора — хуки работают тихо (если не пишут в stdout/stderr), модель их не видит, за исключением специфичных event-output-контрактов.

## Где конфигурируются хуки

Хуки конфигурируются в **`.claude/settings.json`** (project-wide) или **`.claude/settings.local.json`** (локально, обычно в gitignore), под ключом верхнего уровня `hooks`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/example/pre-bash-guard.sh"
          }
        ]
      }
    ],
    "PostToolUse": [ /* ... */ ],
    "UserPromptSubmit": [ /* ... */ ],
    "Stop": [ /* ... */ ]
  }
}
```

Структура:
- Верхне-уровневый объект `hooks`.
- Внутри, каждый ключ — **имя события** (см. каталог ниже).
- Каждое событие мэппится на **массив матчеров**.
- Каждый матчер имеет строку `matcher` (regex или имя инструмента) и массив `hooks` команд.
- Каждая запись команды — `type: "command"` и строка `command` (shell-команда).
- Можно также добавить `timeout` (секунды) отдельным записям команд.

## Lifecycle-события — полный каталог

| Событие | Когда срабатывает | JSON-payload на stdin | Семантика exit-кода |
|---------|-------------------|------------------------|---------------------|
| **`PreToolUse`** | До исполнения инструмента. | `{"tool_name": ..., "tool_input": ..., "session_id": ..., "cwd": ...}` | `0` разрешить; `2` блокировать + stderr модели; другое non-zero = блок с ошибкой. |
| **`PostToolUse`** | После того, как инструмент вернул результат. | `{"tool_name": ..., "tool_input": ..., "tool_response": ...}` | `0` продолжать; другие коды могут предупреждать, но не блокируют. |
| **`UserPromptSubmit`** | Когда пользователь отправляет промпт. | `{"prompt": ..., "session_id": ...}` | `0` разрешить; `2` блокировать отправку + stderr модели. |
| **`Notification`** | Когда Claude требует внимания пользователя (ждёт ввод, нужно разрешение). | `{"message": ...}` | Информационное. |
| **`Stop`** | Когда основной агент заканчивает turn. | `{"stop_hook_active": ...}` | `0` продолжать; `2` говорит модели продолжать работу (редко). |
| **`SubagentStop`** | Когда сабагент (Agent tool) заканчивает. | `{"stop_hook_active": ...}` | То же что Stop. |
| **`PreCompact`** | До того, как харнес компактирует старые сообщения. | `{"trigger": "manual" or "auto"}` | Информационное. |
| **`SessionStart`** | В начале новой сессии. | `{"session_id": ..., "cwd": ...}` | Информационное. |
| **`SessionEnd`** | Когда сессия заканчивается. | `{"session_id": ...}` | Информационное. |

### Паттерны матчеров

- Для `PreToolUse` / `PostToolUse`, `matcher` — **паттерн имени инструмента**. Точные имена: `Bash`, `Edit`, `Write`, `Read`, `Grep`, `Glob`, `WebFetch`, `Agent` и т.д. Также поддерживает regex (`.*` матчит любой инструмент).
- Для других событий `matcher` обычно `""` (пустой — матчит всё) или опущен.
- Несколько матчеров в массиве события — все получают свой шанс; независимы.

## Контракт stdin / stdout

Каждый hook-скрипт:
1. Получает **JSON-payload на stdin** с описанием события.
2. Запускает свою логику.
3. Пишет в **stdout** (обычно игнорируется, если у события нет output-контракта).
4. Пишет в **stderr** (показывается пользователю — или модели для блокирующих событий).
5. Выходит со статусом, определяющим разрешено ли действие.

Ключевое правило: **stderr + exit код 2 — канал блокировки для модели.** Для `PreToolUse`, exit 2 блокирует инструмент И отправляет stderr модели, чтобы она адаптировалась. Используй это для enforce'а project-policy («не запускай `rm -rf`»; «не коммить в main напрямую» и т.д.).

Для событий без блокирующего канала (`PostToolUse`, `Notification`, `Stop` и т.д.), exit-коды отличные от 0 могут дать предупреждения, но не откатят событие.

## Написание hook-скриптов — операционные правила

1. **Держи быстрыми (<1 секунды типично, <5 секунд жёсткий потолок).** Хуки в критическом пути каждого tool-вызова / промпта / события сессии — медленные хуки заметно деградируют UX.
2. **Используй абсолютные пути.** Не полагайся на `$PATH` или относительные пути. Начинай с shebang `#!/usr/bin/env bash` или `#!/usr/bin/env python3`.
3. **Не полагайся на shell-окружение для значений.** Если нужен project-path — используй `$CLAUDE_PROJECT_DIR` (даётся харнесом).
4. **Робастно парси stdin JSON.** Используй `jq`, `python -c` или мелкий script language — не грепай сырой JSON.
5. **Логируй в файл для дебага.** stdout/stderr user-facing для многих событий; используй лог-файл для hook-internal трейсов (`${CLAUDE_PROJECT_DIR}/.claude/hooks/log.txt`).
6. **Делай хуки идемпотентными.** Хук может быть перезапущен (например, после retry). Побочные эффекты должны быть безопасны к повтору.
7. **Fail open для advisory-хуков.** Если auto-format хук ошибся — предпочитай `exit 0` + stderr warning блокировке. Резервируй `exit 2` для настоящих policy-нарушений.
8. **Тестируй хуки без харнеса.** Каждый скрипт должен быть тестируем через `echo '{"tool_name": "Bash", ...}' | ./pre-bash-guard.sh`.
9. **Версионируй скрипты.** Держи их под `.claude/hooks/` и коммить в git.
10. **Документируй каждый хук** в начале скрипта: событие, что делает, ожидаемые поля payload, exit-семантика.

## Типичные паттерны хуков

**Policy enforcement (блокирующий):**
- Блок `Bash`-команд, матчащих destructive паттерны (`rm -rf`, `DROP TABLE`, `git push --force`).
- Блок коммитов/пушей в защищённые ветки.
- Блок записи в secret / config директории.

**Auto-maintenance (не блокирующий):**
- Запуск `prettier`/`ruff`/`eslint --fix` после `Edit` или `Write` на релевантных файлах.
- Запуск `go mod tidy` после правок `go.mod`.
- Регенерация typed API schemas после proto / openapi изменений.

**Audit & observability:**
- Добавление каждого user-промпта + ответа модели в audit-лог.
- Метрики (счётчик запусков хуков, histogram tool-использования).
- Уведомление внешних систем (Slack на Stop-событие, если сессия закончилась ошибкой).

**Safety rails:**
- На `SessionStart` — проверить git working tree матчит ожидаемому baseline.
- На `Stop` — проверить что нет uncommitted изменений в защищённом пути.

## Соображения безопасности

- **Хуки запускаются с привилегиями твоего пользователя.** Зловредный проект может поставить хуки, экспортирующие данные. **Ревьюь хуки в любом склонированном проекте перед доверием.**
- **Хуки наследуют переменные окружения.** Редактируй чувствительные env vars в hook-скриптах (`unset AWS_SECRET_ACCESS_KEY` в начале).
- **Не клади секреты в hook-скрипты.** Хуки чекинятся в репо.
- **Остерегайся shell-injection.** Если хук конструирует команду из ненадёжного ввода (например, путь файла из tool_input) — правильно quote'ай или используй массив.

## Примеры скриптов в этой папке

- [pre-bash-guard.sh](../pre-bash-guard.sh) — `PreToolUse` матчер `Bash`. Блокирует destructive bash-паттерны (rm -rf, force-push в main и т.д.) через exit 2. Шаблон для policy enforcement.
- [post-write-format.sh](../post-write-format.sh) — `PostToolUse` матчер `Write|Edit`. Авто-запускает Prettier/Ruff на модифицированных файлах. Шаблон для auto-maintenance.
- [stop-summary.sh](../stop-summary.sh) — `Stop` событие. Эмитит 2-строчный summary изменений за turn (git diff stats). Шаблон для observability.

## Пример сниппета `settings.json`

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/example/pre-bash-guard.sh"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/example/post-write-format.sh",
            "timeout": 10
          }
        ]
      }
    ],
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/example/stop-summary.sh"
          }
        ]
      }
    ]
  }
}
```

## Сводка best-practices

- **Быстрые. Детерминированные. Идемпотентные.**
- **Exit 0 кроме случаев enforce'а policy.**
- **Используй stderr для model-visible сообщений на блокирующих событиях; stdout обычно игнорируется.**
- **`$CLAUDE_PROJECT_DIR` — твой друг; всегда используй для якорей путей.**
- **Парси stdin JSON через `jq`, не regex.**
- **Держи хуки под version-control и ревьюй во время code review.**
- **Никогда не клади секреты в hook-скрипты — они чекинятся в репо.**
- **Документируй событие, матчер, exit-семантику каждого хука в начале скрипта.**
